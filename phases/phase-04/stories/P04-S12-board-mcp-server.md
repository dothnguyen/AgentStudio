# P04-S12 — Board MCP server

Status: Done (2026-10-24), except the two live-provider steps (the Q10 spike and the one live run), which are prepared as scripts but must be run by the operator with authenticated providers — see Evidence
Depends on: P04-S08 (phases), P04-S10 (scheduler and run-board)
Architecture: [P04 design contract](../README.md#g-board-mcp-server-s12)

## Goal
An agent working an assignment can add tickets (for example the findings of a review) to the board, and list tickets and phases, through an MCP server. Agents never touch the database or files; the coordinator stays the only writer.

## Implement in this order
1. **Spike first (Q10).** With the real Claude Code and Codex CLIs, run a minimal stdio MCP server from a generated per-assignment config inside the sandbox the adapters use today. Record in the story Evidence whether the server starts and whether it can reach the coordinator's command inbox. A provider that cannot is out of scope; say so in the README and stop for that provider.
2. `agent-studio mcp`: stdio JSON-RPC 2.0 server, standard library only. Methods `initialize`, `tools/list`, `tools/call`; errors map to JSON-RPC errors with the command error code in `data`.
3. Tools: `ticket_add` (title, body, priority?, phase?, dependsOn?), `ticket_list` (status?, phase?), `ticket_show` (key), `phase_list`, `board_show`. Each call goes through the validated command path (`request` envelope with an idempotency key), never direct DB access.
4. Team definition: optional boolean `canAddTickets` per member in `teams/<id>.json`, with schema validation, `team add-member --can-add-tickets`, and `team show` output. Default false.
5. Adapters: only for an assignment whose member has `canAddTickets`, the Claude adapter generates a per-assignment MCP config (replacing `--strict-mcp-config` for that assignment only) with an allowlist of `mcp__agent-studio__*` tools; the Codex adapter sets the equivalent `mcp_servers.*` overrides. The server environment carries the assignment id and agent id. Other assignments are unchanged.
6. Coordinator rules for `ticket_add`: the assignment must be active and its member allowed (`FORBIDDEN`); the ticket gets `createdBy` (member id, assignment id), the board's `initial` status, and the requested phase (default phase when omitted; unknown or closed phase is refused); per-assignment cap, default 10 (`TICKET_CAP_REACHED`); a duplicate open title is `TICKET_DUPLICATE`. A repeated call with the same idempotency key returns the first result.
7. `fake_cli` scenario that calls the MCP tools, so the path is testable without a real provider.
8. Docs: README section on enabling it for a member and what agents can and cannot do.

## Evidence

- **No migration for phases/tickets; migration 14** (`schema.MIGRATION_14`, `SCHEMA_VERSION = 14`): `agents.can_add_tickets INTEGER NOT NULL DEFAULT 0` (the flag is runtime team state; the definition stays a file). New codes: `FORBIDDEN`, `TICKET_CAP_REACHED`, `TICKET_DUPLICATE`.
- **The server** (`mcpserver.py`, `agent-studio mcp`): stdio JSON-RPC 2.0, standard library only. `initialize` (protocol `2024-11-05`, serverInfo agent-studio), `tools/list` (the five tools with input schemas), `tools/call`, `ping`; `notifications/*` answered with nothing; unknown method/tool → JSON-RPC `-32601`, malformed frames / wrong `jsonrpc` → `-32600`. Command errors are **tool results** (`isError: true`, `code: <command code>`, the message in `content`), so an agent sees `TICKET_DUPLICATE` etc. directly; protocol-level failures carry `error.code`/`error.data`. Launched per assignment with `AGENT_STUDIO_ASSIGNMENT` / `AGENT_STUDIO_AGENT` / `AGENT_STUDIO_WORKSPACE` in the environment (refuses to run without them). Every tool call becomes the corresponding dispatch command (`ticket.add/list/show`, `phase.list`, `board.show`) through `client.submit` with an idempotency key derived (uuid5) from the JSON-RPC request id + identity + arguments — a retried `tools/call` with the same request id re-derives the same key and the coordinator returns the first result, so one ticket. The server never opens the database.
- **Coordinator rules** (`boardmodel.mcp_ticket_add`, taken by `ticket.add` when the args carry `assignment`): the assignment must be active (queued…reconciling) and its agent row `can_add_tickets` (`FORBIDDEN`, nothing written); per-assignment cap counted from `created_by_assignment` (default 10, `TICKET_CAP_REACHED`); duplicate check against open (non-terminal-status) tickets of the same title (`TICKET_DUPLICATE`); the ticket gets `created_by_member` (member id or agent id) + `created_by_assignment`, the board's `initial` status, and the requested open phase (default when omitted; unknown → `PHASE_NOT_FOUND`, closed → `PHASE_CLOSED`); `dependsOn` keys are linked with a `ticket.depends` event (`TICKET_NOT_FOUND` on a bad key). Receipt deduplication is the coordinator's own idempotency-key behaviour.
- **Team definitions:** optional boolean `canAddTickets` per member — validated by `teamdefs.validate` (`TEAM_CONFIG_INVALID` with `problems`), accepted by `team add-member --can-add-tickets true|false`, shown in the file (hand-editable, unknown keys preserved as always), mapped through `team start`'s roster (`validate_roster` type-checks it) into `agents.can_add_tickets`; old definitions without the key load unchanged. `team add-member` USAGE documents the flag.
- **Runner/adapters:** `tasks.build_request` freezes `mcpTickets: bool(agent.can_add_tickets)` into the request (both dispatch paths), the runner carries it into `AssignmentInput.mcp_tickets`; `providers.base.mcp_launch()`/`mcp_env()` define the shared launch (same interpreter, `-s backend/launch.py mcp`, the caller's state-dir base and env mode, per-assignment identity). **Claude:** `_prepare` writes a per-assignment `mcp.json` next to the prompt file (private 0600) with only the agent-studio stdio server and adds `--mcp-config <file>` beside the usual `--strict-mcp-config` (so the allowlist still means "only what Agent Studio passes"); the process env carries the identity. **Codex:** `mcp_servers.agent-studio.command/args/env` config overrides plus the identity env. Assignments whose member lacks the flag are byte-for-byte unchanged (`mcpTickets: false`, no config, no env) — proven by the second integration test (its request has `mcpTickets: false` and the fake's summary contains no `mcp ok:`).
- **Fake-provider path:** the fake adapter passes `--mcp` and `AGENT_STUDIO_MCP_COMMAND` (the launch argv as JSON) for MCP-enabled assignments; `fake_cli` then spawns the real server exactly as a real CLI would, runs `initialize`, `tools/list`, two `ticket_add` calls (the second a duplicate with the same JSON-RPC id → the same idempotency key → one ticket), one phased call and a `ticket_list`, and reports `mcp ok: …` in its summary. This exercises the full chain: runner env → fake → server → client.submit → command inbox → coordinator → DB.
- **Tests:** `tests/unit/test_p04_s12_mcp_server.py` (11 tests: protocol incl. error codes, tool results with command codes, every §G rule incl. cap/duplicate/terminal-twin/phase/depends, idempotency by request id over a mocked dispatch, the workspace riding every call, `canAddTickets` validation + `add-member` + old-file compatibility) and `tests/integration/test_p04_s12_mcp_run.py` (a board-run fake-provider run whose agent adds two distinct tickets with `createdBy` = member scribe + the claiming assignment, both in the default phase in `initial` status once the run ends; and a plain member's run with `mcpTickets: false` producing no MCP summary). Kept tests updated for v14 only (schema literals in the three migration/lifecycle files; the agents-columns dump in `test_p03_s01_migration`).
- **Docs:** `backend/README.md` gains "The board and its MCP server (P04)" — enabling it for a member, what the server exposes, and what agents can and cannot do; the layout table lists the board modules. RECOVERY.md documents `FORBIDDEN` / `TICKET_CAP_REACHED` / `TICKET_DUPLICATE` (the unit doc check enforces this).
