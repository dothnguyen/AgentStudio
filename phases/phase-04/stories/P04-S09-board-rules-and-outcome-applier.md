# P04-S09 — Board rules and outcome applier

Status: Done (2026-10-24)
Depends on: P04-S07 (generic board model)
Architecture: [P04 design contract](../README.md#design-contract), §D, §E

## Goal
The board rules say who works which status and what happens on pass, fail and blocked. They are validated when loaded, and a finished workflow run is applied to its ticket by those rules.

## Implement in this order
1. Rules schema in `board.json`: `when.status`, `role`, `workflow`, `onPass`, `onFail`, optional `onBlocked`, `maxRounds`, `during`, `cap`, `requiresDeps`, `workspace` (`main|worktree|none`), `action`, `priority`. A rule has `action` or `role`+`workflow`, never both.
2. `board rules check`: every status named exists; every role exists in `roles.json`; every workflow exists and can be bound; the rule graph has a path from `initial` to `done`; at most one rule per `when.status`.
3. Outcome applier: given a finished run (pass, fail, paused/blocked) and its ticket, move the ticket to `onPass`/`onFail`/`onBlocked`, count rounds per ticket and rule, block with a reason when `maxRounds` is hit, and write events. Idempotent: applying the same run twice changes nothing.
4. Ticket keeps the run id it was last applied for, so a late outcome after restart is applied once.
5. `ticket unblock` returns a blocked ticket to its recorded return status.

## Done when
- [x] `rules check` reports each misconfiguration (unknown status, role or workflow, two rules for one status, no path to done) at load time. Test: unit.
- [x] Pass, fail, blocked and round-limit paths move the ticket as configured; a repeated apply is a no-op. Test: unit with synthetic run results.
- [x] A real fake-provider workflow run result is applied through the applier. Test: integration.

## Evidence

- **Migration 12** (`schema.MIGRATION_12`, `SCHEMA_VERSION = 12`): `tickets` gains `run_id` (the run last applied — idempotency for late/replayed outcomes), `rounds_json` ({rule status: count}), `return_status` and `blocked_reason`. Migrations 1–11 unedited.
- **Rules schema** (`boardmodel.load_config`): a rule is `{when: {status}, role, workflow, onPass, onFail, onBlocked?, maxRounds?, during?, cap?, requiresDeps?, workspace?: main|worktree|none, action?, priority?}` with `action` XOR `role`+`workflow`; `onPass`/`onFail` required, `when.status` and every target must be configured statuses; ints (`maxRounds`, `cap` ≥ 1, `priority` ≥ 0), `requiresDeps` bool, `workspace` enum, `during` a slug. At most one rule per `when.status`; the status id `blocked` is reserved (boards may not configure it) and `load_config` indexes rules by status (`rulesByStatus`). All of this fails every board command with `BOARD_CONFIG_INVALID` + `data.problems`.
- **`board rules check`** (`boardmodel.check_rules`, CLI-local in `boardcli` like `team validate`): every role exists in `roles.json` (a missing file is reported as such), every workflow exists in `.agent-studio/workflows` or the built-ins and loads (`workflowdef.load` — "can be bound"), and BFS over the rule graph (when → onPass/onFail/onBlocked edges) finds a path from the `initial` status to a `done` one. Prints `board rules: OK (N rule(s))` or exits 1 with the problem list; `--json` gives the envelope.
- **Outcome applier** (`boardmodel.apply_run_outcome`, dispatch `ticket.apply {workspace, key, run}`, CLI `ticket apply KEY RUN`): reads the workflow run row, maps `succeeded → pass`, `failed → fail`, `paused/cancelled → blocked` (an unfinished run is `TICKET_BUSY`, an unknown one `NOT_FOUND`), finds the rule by the ticket's status (`BOARD_RULE_MISSING` without one), moves to `onPass`/`onFail`/`onBlocked`, counts the round per ticket and rule in `rounds_json`, and blocks with `ROUND_LIMIT:<status>` when a non-pass outcome reaches `maxRounds` (or `RUN_BLOCKED:<run>` for a blocked outcome with no `onBlocked`). Every apply appends one `ticket.outcome_applied` ticket event with run, outcome, rule, round and reason. Idempotent: the ticket keeps `run_id`, so applying the same run again (late after a restart, or replayed) is a no-op that writes nothing; a different run applies normally.
- **`ticket unblock`** (dispatch `ticket.unblock`, CLI `ticket unblock KEY`): returns a `blocked` ticket to its recorded `return_status` (the initial status if none was recorded), clears `return_status`/`blocked_reason`, writes a `ticket.unblocked` event; a non-blocked ticket is `TICKET_TRANSITION_INVALID`. `board show` renders blocked tickets under a reserved `blocked` column (per phase, only when present) and `ticket list --status blocked` accepts the reserved value.
