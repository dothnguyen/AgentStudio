# P04-S04 — Ask and one-off workflows

Status: Done (2026-10-24)
Depends on: P04-S03 (team lifecycle by id)
Architecture: [P04 design contract](../README.md#design-contract), §B, §C

## Goal
The operator asks a free member to do something and runs a one-off workflow with roles bound to members, with no board. The helper operations the operator uses today in `team.py` (`workflows`, `check`, `retry`, `blocked`, `resolve`) become real `agent-studio team` commands. Every new command is a thin CLI wrapper over existing dispatch commands (`team.status`, `snapshot`, `task.direct`, `workflow.list/validate/start/retry`, `assignment.resolve`); no dispatch command, coordinator handler or engine rule changes (constraint 1).

## Implement in this order
1. **Module and team resolution.** Put the new commands in a new module `backend/agent_studio/teamcli.py`, called from `cli._local_command` for `team ask | run-workflow | workflows | check | retry | blocked | resolve`. Every command takes `[--team REF] [--workspace PATH] [--json]` (`--pretty` as everywhere). The runtime team is found exactly like S03 step 6/7: `REF` a UUID → `{teamId}`; otherwise the workspace (`--workspace` as is, else `workspace.resolve(cwd)`) and the definition (`--team ID`, else the only team, else `TEAM_NOT_FOUND` / `TEAM_AMBIGUOUS`), then a read-only `team.status` request. If `data.team` is `null` or its `status` is not `running`: `TEAM_NOT_RUNNING` (remediation `run agent-studio team start --team <id>`) and no inbox request is written.
2. **Member lookup.** `--member REF` and `--bind ROLE=REF` resolve against `team.status` `data.members` with the `teams.find_agent` rules: `agentId` equals `REF`, else `memberId` equals `REF`, else `name` equals `REF` case-insensitively; none is `MEMBER_NOT_FOUND`. Share one pure matcher (e.g. `teams.match_member(rows, ref)` on plain dicts) between `find_agent` and the CLI so the two cannot drift; `find_agent` keeps its behaviour and its S03 tests.
3. **`team ask [--team T] --member M [--policy read_only|workspace_write] [--wait] (TEXT | --text-file PATH|-)`.** Exactly one of the positional `TEXT` or `--text-file` (reuse `cli._task_text` rules; `BAD_REQUEST` otherwise). `--policy` defaults to `read_only`. Sends `task.direct` `{teamId, agentId, policy, text}` with a fresh idempotency key; the coordinator's answer is passed through, so a busy member is `AGENT_BUSY`. Without `--wait`: human `asked <member name>: task <taskId> assignment <assignmentId>`. With `--wait`: follow with `watch.follow` as `task direct --wait` does, then human `<member name> [<provider>/<role>]: <assignment status>` and the result text (`result.finalText`, else `result.summary`). `--json` prints the raw envelope (the receipt, or the followed detail with `receipt` as `task direct --wait` does).
4. **`team run-workflow [--team T] NAME [--bind ROLE=MEMBER ...] [--wait] (TEXT | --text-file PATH|-)`.** First a read-only `workflow.validate` `{teamId, definition: NAME, bindings}` with the `--bind` members mapped to agent ids (`--bind` parsing and duplicate-role rule as `cli._bindings`). An unbound role with no member or several members fails here with the engine's `ROLE_UNBOUND` / `ROLE_AMBIGUOUS` (code and `data.role` unchanged); the CLI replaces the remediation with `pass --bind <role>=<member>` listing the candidate member names; no inbox request is written. Then `workflow.start` `{teamId, definition, text, bindings}` with **every** role bound to the agent ids `workflow.validate` returned. Without `--wait`: human `started workflow <id>` plus one line per binding `<role> -> <member name>`. With `--wait`: follow with `watch.follow_workflow` like `workflow start --wait`, then human output as `team.py run`: bindings, `route: ...`, `status: ...`, the last verdict findings, the last stage summary.
5. **`team workflows [--team T]`** sends `workflow.list` `{teamId}`; human one line per definition: name, `built-in` or `project`, description, `INVALID (N error(s))` when `errors` is non-empty (same fields as `team.py workflows`).
6. **`team check [--team T] NAME [--bind ROLE=MEMBER ...]`** sends `workflow.validate`; human `NAME: OK  stages: a -> b`, one line per binding `<role> -> <member name>`, then `warning: <message> (<path>)` per warning (same as `team.py check`). Writes nothing.
7. **`team retry [--team T] [--workflow ID]`**: without `--workflow`, the newest workflow run of the team (from `snapshot` `{teamId}`, `workflowRuns`, by `createdAt`) whose status is `running` or `paused`; none is `NOT_FOUND` "No running or paused workflow for this team." Sends `workflow.retry` `{workflowRunId}`; human `workflow <id>: stage <stage> retried (new assignment <newAssignmentId>)`.
8. **`team blocked [--team T]`**: from `snapshot` `{teamId}`, the team's assignments that `assignment.resolve` accepts: status `waiting_input` or `reconciling`, plus the current stage assignment of a `paused` workflow run. Human: `No member is waiting for a decision.` when empty; else per item `<member name> [<role>] assignment <id> <status>` (and `workflow <id> paused` when it applies), the result summary (first 300 characters), each attention item, and the `team resolve` commands to free it. `--json`: `data.items [{assignmentId, status, agentId, memberId, member, role, workflowRunId | null, summary}]`. Read-only.
9. **`team resolve [--team T] (--member M | --assignment ID) --action fail|retry|cancel`**: with `--member`, the member's item from step 8 (none is `NOT_FOUND` "No assignment of <member> is waiting for a decision"); with `--assignment`, that id as is. Sends `assignment.resolve` `{assignmentId, action}`; the coordinator's answer (e.g. `RESOLVE_NOT_ALLOWED`) is passed through. Human `<member name>: assignment <id> resolved with <action>`.
10. Human errors follow §B (`CODE: message` plus remediation on stderr, exit 1). Add the seven commands to `USAGE`. `teamcli.py` imports none of `board`, `board_scheduler`, `board_config`, `tickets`, `bugfile`, and sends no `board.*` or `ticket.*` command.
