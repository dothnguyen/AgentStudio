# P04-S03 — Team lifecycle by id

Status: Done (2026-10-24)
Depends on: P04-S02 (team definitions)
Architecture: [P04 design contract](../README.md#design-contract), §B, §C

## Goal
`team start`, `stop` and `status` act on a team definition by id. The runtime team and agents record the definition's team id and member ids, so panes, agent records and `status` say `Ryan`, and several teams (different definition ids) can run in one workspace. The legacy `team.json` start, `--agent` rosters and UUID addressing keep working unchanged (constraint 1).

## Implement in this order
1. Schema: the next migration (expected version 9; `SCHEMA_VERSION` is 8 and `teams`/`agents` have no such columns) adds nullable `teams.def_id TEXT` and `agents.member_id TEXT` with `ALTER TABLE ... ADD COLUMN` only. Rows started without a definition (legacy `team.json`, `--agent`) keep both `NULL`. Record the version in Evidence.
2. `team start` modes, decided in the CLI process (the order matters):
   - `--agent` given: the explicit roster path exactly as today (`--workspace` required); `--team` with `--agent` is `BAD_REQUEST`.
   - Otherwise the workspace is `--workspace PATH` when given (used as is; `workspace.json` is not required), else `workspace.resolve(cwd)` (§A).
   - If `teamdefs.list_ids(workspace)` is non-empty: definition path (step 3). Team selection is S02 step 4 (`--team ID`, else the only team, else `TEAM_NOT_FOUND` / `TEAM_AMBIGUOUS`).
   - Else: `--team` given is `TEAM_NOT_FOUND`; without it the request is today's `{workspace[, name]}` unchanged, and the coordinator reads `team.json` as before.
3. Definition path: the CLI reads the file fresh with `teamdefs.load`, runs `teamdefs.validate`; any problem is `TEAM_CONFIG_INVALID` with `data.problems` and **no request is written**. A team with no members is `TEAM_CONFIG_INVALID` too (problem path `members`). It then sends `team.start` with `workspace`, `name` (`--name` or the definition name), `teamDefId` and `roster` mapped per member: `memberId` ← `id`, `displayName` ← `name`, `providerId` ← `provider`, `role`, and `model` / `reasoning` when set. Agent ids stay fresh UUIDs. The roster is frozen in the request and the DB, so editing the file while the team runs changes nothing until the next `start`.
4. Dispatch and coordinator: `_validate_team_start` accepts an optional slug `teamDefId` and an optional slug `roster[i].memberId` (`BAD_REQUEST` otherwise); `validate_roster` keeps `memberId`. `teams.team_start` writes `def_id` on the team row and `member_id` on each agent row. Pane titles (`"{displayName} [{provider}/{role}]"`) and the agent banner already use `displayName`, so they show the member name; keep that. Per-assignment run logs stay keyed by assignment id (no renaming).
5. One running team per definition id: today `team_start` has no per-workspace limit, so there is nothing to lift. Add a check in `teams.team_start`: if a team row with the same `workspace` and `def_id` has status in `starting`, `running` or `stopping`, the start is `TEAM_ALREADY_RUNNING` (new code in `protocol.py`, data `{teamId, teamDefId}`, remediation `run agent-studio team stop --team <id>`) and nothing is created. Legacy/`--agent` starts (`def_id` NULL) are not limited, as today. The per-workspace/worktree `WORKSPACE_BUSY` write serialization from P00 is untouched (Q8).
6. `team stop [--team REF]`: if `REF` is a UUID it is the runtime team id, exactly as today (`team.py` uses this). Otherwise the CLI resolves the workspace (step 2 rules) and the definition (S02 step 4, `REF` as the id), and sends `team.stop` with `{workspace, teamDefId}`. The coordinator stops the newest team row for that workspace and `def_id` whose status is not `stopped`; none is `TEAM_NOT_RUNNING`. Only that team's session, agents, assignments and tasks are touched (the existing `team_stop` body). Output of `start` and `stop` stays the JSON envelope as today (`team.py` parses it).
7. `team status [--team ID] [--workspace PATH] [--json] [--pretty]`: a read-only dispatch command `team.status` (read path like `snapshot`, not an inbox command), args `{workspace, teamDefId}` resolved as in step 6, or `{teamId}` when given a UUID. It returns the newest runtime team for that definition: `data.team {id, teamDefId, name, status, workspace}` and `data.members [{memberId, name, role, provider, agentId, availability, paneState, assignment: {id, status, taskId} | null}]`, where `assignment` is the agent's assignment in a non-terminal status (`teams.ACTIVE`). With no runtime team ever started for the definition: ok with `data.team: null`, `data.members: []`; human `team <id>: not running`. Human output (S01 `emit`, §B): one line for the team (`<defId> (<name>): <status>`), then one per member (`<name> [<provider>/<role>] <availability>` plus the assignment id and status when there is one). The handler and its module import nothing from `board`, `board_scheduler`, `board_config` or `tickets`.
8. Runtime member lookup for later stories (S04 `--member`): `teams.find_agent(conn, team_id, ref)` returns the agent row whose id equals `ref` (UUID), else whose `member_id` equals `ref`, else whose `display_name` equals `ref` case-insensitively; none is `MEMBER_NOT_FOUND`. It matches `teamdefs.find_member` on the same team (Q7). No CLI command uses it in this story.
9. Add `team status` and the new `start`/`stop` forms to `USAGE`.
